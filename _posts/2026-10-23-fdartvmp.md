Flutter 应用的逆向门槛一向不高。发布版 Dart 代码经 AOT 编译成 `libapp.so`，里面有符号、有常量、有相对完整的控制流，工具链（比如 Blutter）跑一遍就能还原出可读的结构。

[FDartVMP](https://github.com/haothtrteen/FDartVMP) 要解决的就是这一点：**让指定的 Dart 函数在产物里根本不存在。**

## 为什么不能直接套现成的 SO VMP

`libapp.so` 其实不是标准的 NDK 机器码，而是一个 ELF 里装着 **Dart VM 快照**。它没有 `JNI_OnLoad` 入口，通用的 SO VMP 或 DEX VMP 工具套上去会破坏快照结构，应用直接起不来。

所以出路不是去混淆快照里的机器码，而是**把敏感逻辑从 Dart 里搬出去**：

```
核心算法  ──► 私有字节码  ──► 加密  ──► 嵌入 C 层
    │                                        │
    └──► Dart 侧只留一行 stub  ◄── FFI 返回 ◄── 私有 VM 执行
```

逆向 `libapp.so` 的人只能看到一行 stub。真正的逻辑只以字节码形式存在于 native 库中，并且只在一次调用的时间内是明文。

## 编译流水线

```
protected/*.dart              真正的实现（不在 app 里）
      │
      ├── tool/vmpc: 词法 → 语法 → AST → 字节码 → 操作码置换
      │              → 流加密 → 容器
      ├── packages/dartvmp/generated/vmp_module.inc  掩码后的 uint64 镜像
      ├── CMake（Windows 静态链接；Android 出 libdartvmp.so）
      ├── app/lib/generated/protected_stubs.dart     应用调用的一行 stub
      └── Dart FFI → C 解释器（dvmp_vm.c）→ 23 个受审计内建函数
                    └─ 受保护内存：解密 → 执行 → 擦除 → 重新加密
```

## 为什么没用 dart_eval

`dart_eval` 是个好项目，但它省掉的是编译器，留下的是更难的一半：

| | 自研 VM（本仓库） | dart_eval |
|---|---|---|
| 编译器 | 约 1200 行 Dart | 现成 |
| **native 解释器** | 约 700 行 C | **仍然要自己写** |
| 字节码对 Dart 工具链不可见 | 是，从来不是 Dart 对象 | 否，是 Dart `Program` |
| 私有指令集 | 原生实现 | 要 fork 才能改 |
| 结果 | 逻辑真的不在 `libapp.so` 里 | 逻辑只是搬家 |

`dart_eval` 的运行时是纯 Dart，想在 C 层执行它的字节码，等于把 Dart VM 再塞回 C 里——正好是这个设计要避开的东西。所以仓库自己写了一套小指令集和小编译器。

边界留得很干净：只要按 `packages/dartvmp/src/dvmp_wire.h` 的指令集输出字节码，就能接上现有运行时，以后想加 `dart_eval` 前端也不用重做。

## 闭环验证与挑战

这类项目最容易变成"看起来能用"。所以每一环都在测试里：编译器套件、与 Dart 参考实现做差分对比的应用套件、发布 APK 里目标函数不可见的产物检查，以及真机运行。全部走 `tool/test.ps1 -Release`，结果——包括没做成的部分——都写进文档。

仓库还带了一个 CTF 风格的靶子，用的是这个项目最强的配置。规则和预期难度在 [docs/CHALLENGE.md](https://github.com/haothtrteen/FDartVMP/blob/main/docs/CHALLENGE.md)。如果绕过了，欢迎告诉我。
